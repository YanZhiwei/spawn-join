# Harness Phase Context

[简体中文](README.md) | [English](README.en.md)

`harness/context/` 只保存对未来工作有实际影响的材料性上下文。每个已批准阶段最多维护
一个阶段上下文文件，推荐命名为：

```text
phase-<NN>-<phase-slug>-context.md
```

## Create and Update Timing

- 阶段开始且获得所需批准后创建；
- 发生会影响范围、实现方案、接口、依赖、拥有者、验收、验证或风险的发现时更新；
- 阶段交接前复核；
- 不把上下文文件当作聊天记录、进度日志或命令输出转储。

## Materiality Test

只有在遗漏信息可能导致以下结果时才记录：

- 改变已批准的范围或实现方案；
- 让未来阶段重复发现或重新做出决策；
- 影响接口、依赖、不变量或模块拥有者；
- 改变验收条件或所需验证；
- 影响安全、隐私、可靠性、观测、回滚或恢复；
- 隐藏阻塞、未决假设、已接受限制或后续行动。

## Required Provenance

每项材料性记录应尽量关联来源，例如文件、命令、测试结果、评审发现、用户决策或
Spec/Plan/Tasks 路径。不要写入凭据、令牌、密钥或不必要的个人信息。

## Investigation continuity

- 在既有 Explore packet 或 Bug assessment 中维护调查问题、相关假设及证据；Context 只保留
  影响后续阶段的短摘要和准确引用，不新建调查文件、状态机或队列。
- 对材料性假设记清：触发条件、来源版本/快照、能区分候选解释的测试/观察、支持或否定的
  理由，以及剩余问题和拥有者。没有区分性验证时仍是未决，不写成确认根因。
- 保留已否定假设及其依据，恢复工作时先核对适用版本，避免把旧方案再次当作新发现。
  相同上游来源的多个摘要只算一个证据来源；冲突不以投票解决。
- 研究在足以支持当前决策、材料性冲突已解决或明确阻塞时停止。时间/资源耗尽不代表
  readiness；关键缺口交回原 owner，非关键限制按现有 Gate 处理，不加审批层。

## Phase handoff

按 [角色导航](../../docs/architecture/repository-map.md#role-based-reading) 找入口，具体 SD 交接
仍使用已安装 [Phase handoff](../../.specify/extensions/delivery/templates/exploration.md#phase-handoff)
及接收角色的原生 packet，不新增统一回执格式。没有 SD run 的 Lightweight 只需比例适当的
范围、来源和验证说明，不为填字段创建 run 或 Feature。

一次真实交接说明：接收角色/问题、允许操作和路径、准确批准来源及实际审批状态、必读的
路径与章节/符号及其权威/相关性、条件阅读触发器、已有输入/需求快照、预期证据和退回条件。
用户要求、Agent 补充解释、假设和未决问题分开；既有决定不靠改写摘要重新解释。

接收方核验必读来源及身份后再判断，并在原生结果中解释来源怎样支持结论。缺失、过期或
冲突的关键输入应返回准确缺口及恢复路径；允许的只读调查可继续，不能把缺口记成 pass。
例行派发引用原批准快照；材料性变化走原 owner 的刷新/审批流程，不修改旧哈希迁就新内容。

## Source-of-Truth Boundaries

- 阶段 Build 文件拥有批准范围、非目标、验收和计划验证；
- Context 文件拥有材料性发现、决策、约束和未决问题；
- `harness/build-log.md` 拥有实际进度和观察到的验证证据；
- Review 文件拥有详细评审发现和签核状态；
- 不要把这些文件互相完整复制，只在必要时使用短摘要和链接。
